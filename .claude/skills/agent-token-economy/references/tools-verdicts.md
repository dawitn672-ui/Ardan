### 1. Ponytail
- **What it is:** an MIT-licensed prompt/skill by DietrichGebert (repo `DietrichGebert/ponytail`, README read at raw.githubusercontent.com/DietrichGebert/ponytail/master/README.md): `skills/ponytail/SKILL.md` plus a compact `AGENTS.md`, "write only what the task needs", never cutting validation, error handling, security or accessibility. Levels lite/full/ultra (`/ponytail [lite|full|ultra|off]`), extra commands `/ponytail-review`, `-audit`, `-debt`, `-gain`. Install in Claude Code: `/plugin marketplace add DietrichGebert/ponytail` then `/plugin install ponytail@ponytail`. Config at `~/.config/ponytail/`. It is "active every session": an always-on ruleset, so it adds a fixed block of context to every turn of every agent. The README does not state hooks for Claude Code (two lifecycle hooks are named for Codex) and does not state telemetry or network calls; only "band data stays local by default". Not read: INSTALL.md, the plugin's hook scripts.
- **Evidence:** the project's own benchmark: 39 tasks, Opus 5.5, 5 runs each: -53% code, -41% time, -26% cost, -45% tokens (earlier README versions: -54% code on 12 tasks, Haiku 4.5, n=4). **Independent: JetBrains, 80 paired tasks** (https://blog.jetbrains.com/ai/2026/07/ponytail-skill-claude-tested/; the page returned 403 to my fetch, numbers come from search-result excerpts of it, so re-read before quoting): -15% code (p=0.088, soft), **-10.3% cost** (p=0.004; cheaper on 46 tasks, dearer on 34), -11% time; code cut only where there was room to over-build; secondary reports (Habr, Capital & Compute, not read in full) say quality was equal on 65 of 80 tasks, 6 better, 9 worse, and that copying only SKILL.md produced no effect (zero activations in ten sessions) so the plugin's forced context is what works.
- **Fit for Ardan:** Ardan's expensive output is not feature code bloat; it is bulk data, long outputs and agent count. The house rules already demand "no gold-plating", small steps, and `ardan-dev-process`. An always-on ruleset on five agents adds tokens to each turn to save about 10% on tasks that have room to over-build. It also could fight order-driven work (events must keep release text exactly; "write less code" can cut required tests, records, and the lint chain).
- **Verdict: adapt the idea, skip the plugin.** Add one line to builder briefs: "smallest change that fully solves it; no new abstraction, config or file the order did not ask for; answer in under 300 words unless asked". Costs nothing, no hook. Reconsider the plugin only after a measured A/B on one Ardan wave.

### 2. /rewind (checkpoints)
- **What it is** (https://code.claude.com/docs/en/checkpointing, commands page): a checkpoint is made at each prompt that starts a turn; `/rewind` (aliases `/checkpoint`, `/undo`; Esc Esc on an empty prompt) offers: restore code and conversation; restore conversation only; restore code only; **summarize from here**; **summarize up to here**. After a restore the chosen prompt returns to the input box for re-sending. Checkpoints are saved with the conversation, a resumed session can still rewind, and rewinding keeps the prompt cache prefix (levers.md 1).
- **Limits:** only files Claude edited with its own file tools; Bash-made changes are undone only in files the main conversation had already edited with Write/Edit, a file touched only by Bash is not tracked (use git); subagent edits not tracked (except foreground `context: fork` skills), reverted only in files the main conversation had already edited; same session only; directory create/move/delete not undone; symlinks and changed directories are skipped with a warning. Cloud sessions: it works there (the web page's only rewind note is an error for self-hosted runners older than v2.1.246), but a cloud container is wiped, so the file backups last only as long as the session's environment, and Ardan's builders work through Bash (`node tools/...`, sed) and subagents, which is exactly what it does not track.
- **When it beats correcting around a failure:** a wrong turn leaves the failed attempt in context for every later turn; rewinding to before it drops that, keeps the cache, and costs one re-sent prompt. Use it when the approach was wrong (not a typo), the dead end was long, and the changed files were edited by the main conversation. Not for work done by subagents or Bash: use `git restore` or `git reset` on the worktree branch (we commit after each step, so the commit is the real checkpoint). "Summarize from here" is a cheaper partial compact.
- **Verdict: owner-only command; adopt for the owner's own interactive sessions and as a doctrine line:** "after a failed approach, rewind (or reset to the last step commit) instead of piling corrections on it". Agents cannot press it; for them the equivalent is the per-step commit already ordered.

### 3. /compact
- **The "up to 85%" claim:** no official page states 85% as a saving or a threshold. A search found only an unofficial page describing a warning at 85% usage; other third-party figures range 64% to 95% for the auto trigger, and a leak analysis says about 83% of a 200K window. Treat 85% as unsourced. Official facts: compaction summarises history; **project-root CLAUDE.md and auto memory are re-injected from disk**; nested CLAUDE.md and `paths:` rules reload on demand; the summary keeps requests and key snippets but "detailed instructions from early in the conversation may be lost" (how-claude-code-works, glossary, memory pages); invoked skills survive within 5,000 tokens each / 25,000 total, most recent first (levers.md 3); up to five recent files come back, a file over 5,000 tokens as a path only.
- **Custom instructions, both routes are official:** (a) the command's argument: `/compact focus on the API changes` (works in cloud sessions: `/compact keep the test output`); (b) a section in CLAUDE.md: the costs page names it `# Compact instructions` ("please focus on test output and code changes"), the agent-loop page says the header name "isn't special; use any clear label" and shows a list of what to preserve (objective and acceptance criteria, file paths read or modified, test results and errors, decisions and reasoning). Also `/rewind` > "Summarize from here / up to here" for a partial compact.
- **Auto-compact settings:** `autoCompactWindow` (tokens, at least 100000, settings file); `/autocompact 500k` (saved per model in `modelSettings`, v2.1.288+); `claude --autocompact` (v2.1.221+); `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (scripts and cloud, wins over the others); `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (1-100, can only lower the trigger, applies to subagents too). **In cloud sessions the platform sets the PCT override itself and overrides one you add**, so compaction fires partway through the window; to change it set `CLAUDE_CODE_AUTO_COMPACT_WINDOW` on the environment. Docs also warn of a thrashing stop when one huge file or output refills context after each summary. Cost: compacting after a cold cache is one big uncached request (levers.md 4); compaction invalidates the cache prefix.
- **What is lost:** early conversation instructions, exact tool outputs, reasoning, files not recently read. What is kept: CLAUDE.md, summary, recent files.
- **Verdict: adopt (adapt the CLAUDE.md route).** Add a `# Compact instructions` section to CLAUDE.md (the lever-7 item, still not added; it is the integrator's file): "keep the current order and acceptance, the branch and last commit sha, files changed, failing test names with first error line, decisions with D-numbers, what is next; drop command output". Builders compact at a step boundary only.

### 4. /handoff
- **What it is:** not a built-in command (commands page has none; a search found only community skills). Several skills implement it: mattpocock/skills `handoff` (MIT, the most prominent; read through a fetch of its SKILL.md), claude-code-engineer, Continuous-Claude-v3 `create-handoff`, and others, which write `HANDOFF.md` at the root, `.claude/handoffs/`, `~/.claude/handoff/HANDOFF-<time>.md` or a memory file. They differ; check each file before use.
- **mattpocock's:** manual only (the model cannot trigger it); packages the conversation into one document for a fresh agent: a summary, a "suggested skills" list, **pointers (path or URL) to existing artifacts (specs, plans, ADRs, issues, commits, diffs) instead of copying them**, redacts keys and personal data; optional argument says what the next session will do; writes to the **OS temp directory** (`TMPDIR` or `/tmp`), not the workspace. The text does not say how a new session finds it: you give the path or paste it. In our wiped containers a `/tmp` file is lost, so as shipped it cannot cross sessions here.

Write the note into the repo on the step branch (or one Notion page) with a fixed 10-line template (done, next, files with lines, tests, open questions), commit it, and make the next brief start "read docs/handoff/<x>.md". Our own `docs/HISTORY.md` end-of-file entries already do half of this; a short template in `ardan-dev-process` is enough. (Already noted above as the mattpocock row's verdict; this fixes the destination.)

### 5. 9router
- **What it is:** `decolua/9router` (https://github.com/decolua/9router, README read; many forks exist, so which copy is named matters; the DEV post https://dev.to/mihailoff/9router-route-claude-code-cursor-or-copilot-through-whichever-free-tier-youve-got-4m61 describes setup). A self-hosted local proxy (`http://localhost:20128/v1`, dashboard, Docker option) that translates between OpenAI, Claude and Gemini formats and chains "combos": use a **subscription** first (OAuth logins for Claude Code, Codex, Copilot, Cursor, with automatic token refresh), then cheap providers (GLM, MiniMax, DeepSeek, OpenRouter, 40+ by API key), then free tiers (Kiro, OpenCode Free, Vertex trial credits). MIT; the README calls the repo package private. Claude Code is pointed at it with `ANTHROPIC_BASE_URL`.
- **Traffic and servers:** model requests go from your machine directly to the upstream you configure, **but the model that answers can be any cheaper or free model**, so a Claude Code session may silently run on a non-Claude model when the first tier runs out (combos substitute by design). **Cloud Sync sends providers, combos and settings (credentials among them, "encrypted storage", details unstated) to `9router.com` by default.** Optional extras: RTK input compression (claims 20-40% fewer input tokens, on by default, falls back if a filter fails), Caveman (claims up to 65% fewer output tokens), Ponytail; none has a measured source in the README. Telemetry: not described; analytics local in SQLite; request logs off by default.
- **Security, bluntly:** default first-login password `123456` unless `INITIAL_PASSWORD` is set; fixed placeholder secrets (`API_KEY_SECRET`, `MACHINE_ID_SALT`); `REQUIRE_API_KEY` off by default; example configs bind `0.0.0.0` (open to the network). It stores your subscription OAuth tokens, i.e. the keys to the owner's Claude account. The README claims "unlimited FREE AI coding / never hit limits" while its own page caps free tiers and lists free tiers that were shut down: marketing is unreliable.
- **Terms of service:** Anthropic's Claude Code legal page (https://code.claude.com/docs/en/legal-and-compliance.md, read via search excerpt) says OAuth authentication is for ordinary use of Claude Code and other native Anthropic applications, and Anthropic does not permit third parties to route requests through Free, Pro or Max plan credentials on behalf of users; the Consumer Terms add that OAuth is only for Claude Code and Claude.ai, and Anthropic has said publicly (The Register, 2026-02-20, https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access) that third-party harnesses on subscriptions are prohibited, with account action possible. Routing the owner's subscription token through 9router is that case. Using it with a paid **API key** is allowed by Anthropic's terms but then saves nothing on Claude (it only forwards), and any cheaper model it substitutes changes quality and the repo's model plan (D-009).
- **Cloud containers:** our sessions run in Anthropic's VM behind an allowlisted proxy; a localhost router would have to run inside each wiped container and its hosts be allowed; the owner's local machine is the only place it could live, and then it sits between every session and the account.
- **Real savings:** only by swapping Claude for cheaper models (a quality change, not a saving) or by RTK/Caveman filters, claims unmeasured, and the `| tail` rule already gets RTK's gain (see rtk row above).
- **Verdict: skip.** Not recommended on risk grounds alone (account ban risk, credential store with a default password, silent model substitution, a third-party server holding settings). If the owner wants cheaper output, use Haiku or Sonnet default by job (SKILL.md lever 3), which is the same saving with no proxy.

### 6. Obsidian vs graphify vs Notion vs GitHub
- **Facts:** an Obsidian vault is a folder of plain markdown files with `[[links]]`; the app is free and the optional Sync is paid (about $4 a month billed yearly per Obsidian's own post https://obsidian.md/blog/standard-plan/; sources conflict on whether commercial use needs a paid licence: check https://obsidian.md/pricing). Agents do not need the app: Claude Code reads the files directly; MCP servers exist (MCPVault `npx @bitbonsai/mcpvault@latest <vault>` and obsidian-mcp read the files with Obsidian closed; others need the app and its Local REST API plugin running, so they cannot work in our container). graphify (earlier row) writes an `obsidian/` folder and, with `--wiki`, markdown articles plus an `index.md` as outputs, so the two are not rivals: graphify is a generator, Obsidian is a viewer of markdown. Docs and images go through a model in graphify (cost). I could not verify Notion free-plan search limits from official pages (search returned none); the owner's note stands.
- **Cost model (Ardan's container is wiped each session):** an agent's cheapest accurate read is a file it can `grep`/`sed -n` in the repo: content once, no echo, no tool overhead, version-controlled, always present after the clone. A vault outside the repo needs a sync step into the container (git repo, or an MCP to a hosted copy) and Obsidian Sync does not reach a Linux container. Notion: reads return the page, writes echo ~900 tokens a row; its value is the owner's own reading and structure, not agent reads. A graph or vault adds a build step per session for little: our docs are already indexed by `docs/README.md` and `tools/lint-docs-index.mjs`.
- **What the owner gains or loses:** Obsidian gains: offline, fast graph view and backlinks for his own thinking, no write-echo cost, plain files. Loses: nothing the agents currently use, but it is a second place for the truth (order 76 wants one reference set), no phone-friendly sharing like Notion's, and Sync cost if wanted on iPhone. Notion gains: structure, phone, order 102 as written; loses: agent read/write cost and free-plan search limits.
- **Recommendation: both, with a split, no new graph tool.** (1) Agents' working knowledge stays in the repo as markdown (`docs/`, skills), read by file; that is the cheapest accurate read. (2) The owner may open the repo's `docs/` folder in Obsidian as a vault at no cost (a vault is just a folder: nothing to install for agents, no sync), giving him graph view and backlinks over the same files; the repo stays the source. (3) Notion keeps what the owner reads and arranges (Chronicle, indexes, decisions summary), written in few rich pages by script (notion.md), not row by row. (4) Skip graphify and any code graph (earlier verdict). **Realistic token effect:** Obsidian-as-viewer saves nothing in agent tokens and costs nothing; moving agent knowledge from Notion reads/writes to repo files saves the ~900-per-row echo (95-99% on bulk, lever 1) and the search cost, and is where the real gain is; a vault plus MCP would add a tool listing (names only, deferred) and a server to start each session for no gain over `grep`.
